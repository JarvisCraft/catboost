# Конспект статьи `paper.pdf`

А. Д. Миронов, «Оптимизация применения oblivious решающих деревьев на ЦП», ВКР,
ФКН НИУ ВШЭ, 2022. Код: `../../catboost-cpu-evaluation-optimization`
(на GitHub — `alexmir1/catboost-cpu-evaluation-optimization`).

## Что измерялось

* Модель `epsilon8k_64`: бинарная классификация, **2000** числовых признаков,
  **64** порога на признак, **8000** деревьев глубины **6**.
* Процессор Intel Ice Lake, **один поток**. Замеры — тысячи повторов, итог —
  среднее CPU time. Все реализации собирались с флагами AVX-512, чтобы поставить
  их в равные условия (значит, SSE/AVX2 цифры в статье могут быть чуть
  оптимистичнее реальных).
* Baseline — опубликованный на GitHub CatBoost.

## Три стадии применения

1. **Бинаризация** — числовые признаки → однобайтовые квантили. Внешний цикл по
   признакам, внутри по объектам блока, внутри по порогам. Результат —
   матрица `число бинарных бакетов × размер блока`, признако-мажорная.
2. **Подсчёт индексов** — по бинарным признакам собирается индекс листа для
   каждого объекта: `index |= (quantile >= border) << depth`.
3. **Загрузка значений листьев** — по индексам берутся ответы (`double`) и
   суммируются по деревьям.

## Результаты (батч 1024 объекта, отклонение от baseline)

Только строки без FP16 — то есть без потери точности:

| Расширение | Загрузка листьев | Блок | Транспонированный | Нетранспонированный |
|---|---|---|---|---|
| SSE (baseline) | наивная | 128 | 0 % | 0 % |
| AVX2 | наивная | 64 | −12 % | −24 % |
| AVX2 | наивная | 128 | −22 % | −23 % |
| AVX2 | наивная | 256 | **−44 %** | +18 % |
| AVX2 | gather | 256 | −43 % | +17 % |
| AVX-512 | наивная | 128 | −19 % | −23 % |
| AVX-512 | наивная | 256 | −42 % | +19 % |
| AVX-512 | наивная | 512 | −42 % | +35 % |
| AVX-512 | gather | 512 | −48 % | +29 % |

С FP16 в листьях (с потерей точности) перестановки дают −71 % / −50 %.

## Ключевые выводы

* **Размер блока важнее ширины регистров.** Для транспонированного входа время
  монотонно падает с ростом блока (128 → 512), для нетранспонированного оптимум
  — 128, дальше деградация. Причина чисто в памяти: при транспонированном входе
  строка признака внутри блока лежит подряд, и чем больше блок, тем реже переходы
  между далёкими строками; при нетранспонированном на каждый объект блока
  читается своя кэш-линия, и блок 128 ещё влезает в L2.
* **256-битные регистры дают ~20 %, 512-битные поверх них — почти ничего**
  (на Ice Lake; там даунклокинг на AVX-512). Основной выигрыш — от ширины
  вообще, а не от AVX-512 конкретно.
* **Gather не даёт заметного выигрыша** перед наивной загрузкой листьев.
* **Перестановки (`vpermpd`) 64-битных значений только замедляют**: число
  операций растёт как O(2^h).
* **Хвосты лучше обрабатывать SIMD, а не скаляром.** На графиках зависимости
  времени от числа объектов видно, что недозаполненный вектор дешевле, чем
  несколько скалярных итераций. AVX-512 маски делают это бесплатно.
* Максимальная эффективность достигается, когда размер батча кратен размеру
  блока (нетранспонированный) или равен ему (транспонированный).

## Что из этого взято в текущую реализацию

* AVX-512 подсчёт индексов и бинаризация — да.
* Маскированные хвосты вместо скалярных — да.
* Блок 512 для транспонированного входа — да (только когда активен AVX-512
  эвалюатор, см. `implementation.md`).
* Gather для листьев — да, но статья предупреждает, что выигрыш мал.
* FP16 в листьях — **нет**: это меняет численный результат модели, а задача
  такого размена не ставила.
* Перестановки FP64 — нет, статья показала, что они медленнее.
